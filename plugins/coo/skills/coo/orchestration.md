# Workflow orchestration: working agreement

The working agreement for multi-workstream or cross-repo work under the `/coo` skill.

- **Workers.** The main session dispatches, checks and reports; it does not write code, migrations or scripts. Implementers and reviewers are ephemeral fire-and-forget subagents, one task each, in isolated worktrees. A worker that needs two-way steering mid-run, watching, or the user attaching to it runs as its own Claude session in a split herdr pane: `pane split`, then `pane run "claude --model <m>"`; steer it with `send-text`. For push-style completion, background `herdr pane wait-output <pane> --regex '(?m)^\s*(⏺\s*)?MARKER\s*$' --timeout <ms>` on the worker's completion marker, then `herdr pane read`. In a Herdr app terminal (`HC_TERMINAL_ID` set, `HERDR_ENV` not set), the `herdr` commands reach the TUI server, not the app's terminals: follow the app section of the `herdr` skill instead (open a shell tab, then start `claude` in it; a session started with `hc run` gets no tab and starts logged out). An unattended pane session can stall on a permission prompt: use project allowlists or `--permission-mode` at launch, plus a stall watcher. Pane ids are not durable, so read them again before each send.
- **Named teammates.** Do not pass `name:` on a bounded dispatch. Un-named background subagents still notify on completion; `name:` adds only SendMessage addressing and idle-notification noise. Use named teammates only when herdr is unavailable and live steering is required, and say why: they are flaky (crossed or dropped messages, silent idling) and the user cannot see them.
- **Model per dispatch.** Pass `model:` on every `Agent` dispatch and name the model in the dispatch description. The core rules' Workflow line "Pick the model" says which model fits which job. Do not trade quality for quota: a frontier-grade task runs on opus (or Fable when opus fell short), or it waits for the quota to reset.
- **Advisor.** An advisor subagent reviews the plan before the first state-changing edit only when a cheaper model wrote the plan or the operation is irreversible or long-arc. When the orchestrator is a frontier model planning routine reversible work, skip it; the adversarial review stays the standing gate.
- **Adversarial review before every PR.** On the branch, all as subagents: the implementer, then the simplify pass (code-simplifier agent), then a hostile reviewer on the worktree, before `gh pr create`. The PR then opens with reviewed code, so CI runs once. The reviewer verifies every claim against live data (it does not trust the implementer's report), lists 5 to 8 specific attack surfaces, and gives CLEAR or BLOCK with file:line, ranked by severity. On BLOCK, fix on the branch and run a delta review before the PR opens. After two review rounds, do not start a third on your own: give the user the open findings as a count by severity, and ask. Fix a non-blocking finding on the branch only when it is inside the PR's scope and the fix is small. Any other non-blocking finding gets a tracker row, and so does one that needs a decision, a migration or another owner. So an implementer brief ends before the PR. The hostile reviewer replaces the built-in /code-review skill, and the simplify subagent replaces /simplify, because those skills run inline and the role split forbids that. One hostile reviewer is the default and suffices for most PRs, engine work included. Escalate to a Workflow-based panel (parallel finders and refute-voting verifiers, all subagents) only when one reviewer's blind spots are the main risk: irreversible data operations, security-boundary changes (auth, RLS), or a diff too broad for one context. Name the review tier in the reviewer's dispatch description.
- **Supervised irreversible operations.** Prove the write surface by reading the code. Then a dry-run gate (the projected delta is explainable), hard-stop predicates written into the brief, freeze on failure (capture state, touch nothing, the user decides recovery), and idempotent recovery paths. Fail closed: silent success is the one failure you cannot afford. Plan a supervised shakeout window after any flip.
- **Irreversibility is the gate.** Reversible and read-only work goes on without asking. Prod writes, schedule changes, deletions and scope changes wait for the user's decision. Domain questions go to the user with the data to answer them; check the user's domain rules against the rules the code actually applies. Do not report someone else's action as done without their confirmation.
- **Watchers and continuity.** Completion notifications are unreliable for long jobs. Use redundant monitors (the agent's own watcher plus an orchestrator marker monitor), check that each monitor works, and kill stale ones. Poke a stalled agent with a status summary and a resume message. Write handoff prompts for the next model's strengths.
- **Loops.** Loop kinds: turn-based (manual), goal-based (iterate to a verifiable success condition), time-based (recur) and proactive (event- or schedule-triggered, no human); `/loop`, `/schedule` and `/goal` cover them. Use goal-based and proactive loops (dependency upgrades, PR triage) on purpose.
- **Extraction.** A pattern in this file becomes its own skill only when it is used outside orchestration about 3 or more times and has grown into a real procedure (its own steps, templates and gotchas).
- **Open-item hand-off.** When the open-items tools are listed, load `handoff_items` and `take_items` with ToolSearch if they are not callable yet. Call `handoff_items` before you start a successor session, and put the code and the URL of the session artifact in the successor's prompt. The session artifact is the one artifact page that holds the session's detail (tables, diffs, long step lists); keep one per session and update it in place. The successor's first step loads `take_items` with ToolSearch and calls it with the code.
